# Career detail atomic exposure

Career detail exposure is fail-closed against the same cache-readiness contract used by the coverage audit. A target locale is ready only when its detail payload is available through `ready_active`, `ready_lkg`, or `legacy_migratable` state.

The required release order is:

1. build the detail projection;
2. stage an immutable detail payload and its exact exposure-projection snapshot for every target slug and locale without exposing an active/LKG pointer;
3. verify every staged payload, matching projection snapshot, and post-promotion gate;
4. commit runtime projection flags such as `detail_route_enabled` and `dataset_visible`;
5. atomically activate the prepared detail pointer batch with pointer restoration on failure;
6. rebuild and activate the locale directory read model.

`CareerRuntimePublishProjectionValidator`, the canonical promotion rollback gate, and the post-promotion release gate reject exposure with `detail_cache_not_ready_for_exposure` or `post_promotion_detail_cache_not_ready` when the target locale is not ready. Apply prepares only the bounded promotion batch from its explicit post-promotion projection while database exposure remains uncommitted. The prepared immutable versions are verified without publishing active pointers, so a concurrent candidate request cannot purge them. After database commit, the full prepared pointer batch is activated under deterministic locks with snapshot restoration on failure, and only then is the directory activated. The activation lock re-verifies both the immutable detail payload and its matching published projection snapshot before switching any pointer; eviction of either staged value blocks the entire batch. Before activation, candidate or temporarily stale materialized-projection reads remain 404. After activation, the detail route may use only the exact published projection snapshot whose version matches the verified active detail payload, so it becomes readable at the same exposure boundary as the directory instead of waiting for a later artifact export. A normal published materialized projection remains preferred when available. It never performs a synchronous full-corpus rebuild.

For ordinary targeted warming, detail payloads are warmed before the full directory/index warm so the newly activated directory observes the final locale readiness state. Promotion-driven list activation overlays the exact validated post-promotion projection onto both the public job-index and directory payloads, snapshots the previous job-index values, verifies the new job-index caches, and then activates the staged directory pointers under the same locale locks. Any job-index or directory failure restores both cache families before remediation, so `promoted_success` means the list API and directory agree. While the materialized artifact remains stale, later directory-only and broad authority warms enumerate missing members from the current active directory and preserve only those backed by a still-active detail payload plus its exact same-version published exposure snapshot. This prevents a warm from regressing a successful promotion without treating the prior directory as authority. Multi-locale directory activation acquires every target-locale rebuild lock before building payloads or inspecting detail readiness, then stages and verifies every immutable locale payload before switching any active pointer. If a later pointer switch fails, all active/LKG/activation metadata touched by the batch is restored, so a partially activated directory cannot advertise a remediated promotion. If detail or directory activation fails after the database commit, the prepared exposure snapshots are removed immediately so stale candidate authority fails closed; the execution result records `writes_database=true`, `database_commit_succeeded=true`, and does not claim `promotion_rolled_back=true` unless remediation is verified.

The directory keeps public/indexability authority separate from runtime detail readiness. An otherwise eligible occupation remains a directory member when a transient cache loss occurs, but its `detail_ready` field becomes `false` on the next directory rebuild. This runtime state never deletes or rewrites CMS content, occupation records, publication authority, sitemap, llms, canonical, noindex, or JSON-LD authority.

This change performs no production promotion, cache repair, CMS/database mutation, or deployment. Runtime monitoring and controlled repair belong to `CAREER-DETAIL-DEPLOY-SLO-REPAIR-01`.
